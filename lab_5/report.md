## 3. Теоретическая часть

### 3.1. Транзакции и свойства ACID

**Транзакция** — последовательность операций, которая выполняется как единое
неделимое целое: либо применяются все её изменения, либо ни одно. Транзакции
обладают свойствами ACID:

- **Atomicity (атомарность):** принцип «всё или ничего». При ошибке на любом шаге
  все изменения транзакции откатываются.
- **Consistency (согласованность):** транзакция переводит базу из одного корректного
  состояния в другое, не нарушая ограничений целостности.
- **Isolation (изоляция):** параллельные транзакции не видят незафиксированных
  изменений друг друга, а их совместный эффект эквивалентен некоторому
  последовательному выполнению.
- **Durability (долговечность):** после `COMMIT` изменения сохраняются даже при
  последующем сбое сервера.

Транзакция начинается командой `BEGIN` и завершается:

- `COMMIT` — фиксирует изменения и делает их видимыми и постоянными;
- `ROLLBACK` — отменяет все изменения и возвращает базу к состоянию до начала
  транзакции.

Команда `SAVEPOINT` создаёт внутри транзакции точку, к которой можно частично
откатиться:

```sql
BEGIN;
UPDATE products SET price = price + 100 WHERE id = 1;
SAVEPOINT after_first_update;
UPDATE products SET price = price - 50 WHERE id = 1;
ROLLBACK TO SAVEPOINT after_first_update;
COMMIT;
```

После `ROLLBACK TO SAVEPOINT` первое изменение сохраняется, а второе отменяется.
Вне явного `BEGIN` каждая команда выполняется в режиме автокоммита.

### 3.2. Изоляция и MVCC

PostgreSQL поддерживает уровни изоляции `Read Committed` (по умолчанию),
`Repeatable Read` и `Serializable`. В PostgreSQL используется MVCC
(многоверсионное управление конкурентным доступом): читающие транзакции видят
согласованный снимок данных и не блокируют пишущие. Для предотвращения
конфликтов при изменении одной и той же строки применяются блокировки, например
`SELECT ... FOR UPDATE`.

### 3.3. Функции PL/pgSQL

Функция в PostgreSQL — именованный серверный объект, который принимает аргументы,
выполняет код и возвращает значение. PL/pgSQL расширяет SQL процедурными
конструкциями:

- `DECLARE` — объявление локальных переменных;
- присваивание `:=` и `SELECT ... INTO`;
- ветвление `IF ... THEN ... ELSE ... END IF`;
- циклы `LOOP`, `WHILE`, `FOR`;
- `RETURN` — возврат значения;
- `RAISE EXCEPTION` — возбуждение исключения и откат изменений;
- блок `EXCEPTION` — перехват и обработка ошибок;
- `RAISE NOTICE` — вывод диагностического сообщения.

Функция объявляется с указанием возвращаемого типа `RETURNS` и языка `LANGUAGE
plpgsql`. Тело функции заключается в блок `BEGIN ... END`.

### 3.4. Триггеры

**Триггер** — серверный объект, который автоматически вызывает триггерную функцию
при изменении данных в таблице. События: `INSERT`, `UPDATE`, `DELETE`; для
представлений используется `INSTEAD OF`.

- `BEFORE` — срабатывает до операции; позволяет проверить или скорректировать
  данные.
- `AFTER` — срабатывает после операции; удобен для аудита и пересчёта связанных
  данных.
- `FOR EACH ROW` — вызов на каждую затронутую строку.
- `FOR EACH STATEMENT` — один вызов на весь оператор.

В триггерной функции доступны псевдозаписи `NEW` (новая версия строки) и `OLD`
(прежняя версия). Триггеры применяют для аудита, валидации, автоматического
заполнения вычисляемых полей и поддержания денормализованных значений.

### 3.5. Логика в базе данных и в приложении

На стороне СУБД уместно держать логику, неразрывно связанную с целостностью:

- транзакционное оформление заказа и списание остатка;
- проверки, которые должны выполняться одинаково для всех клиентов;
- аудит изменений;
- поддержание денормализованных полей;
- расчёт сводных показателей, если он должен быть единым для всех приложений.

В приложении обычно остаются:

- пользовательский интерфейс и сценарии взаимодействия;
- уведомления, рекомендации, маркетинговые правила;
- интеграции с внешними сервисами;
- оркестрация нескольких бизнес-операций;
- логика, которая часто меняется и требует быстрого развёртывания.

Серверный код сложнее тестировать и отлаживать, он привязывает решение к конкретной
СУБД и требует дисциплины версионирования. Поэтому в базе обычно оставляют
инварианты и критичную целостность, а прикладную бизнес-логику — в приложении.

## 5. Реализация серверной логики

### 5.1. Таблица аудита и денормализованное поле рейтинга

Для аудита цен создаётся таблица:

```sql
CREATE TABLE IF NOT EXISTS product_price_audit (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_id  BIGINT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
    old_price   NUMERIC(12, 2) NOT NULL,
    new_price   NUMERIC(12, 2) NOT NULL,
    changed_at  TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT now(),
    changed_by  TEXT NOT NULL DEFAULT current_user
);
```

Для среднего рейтинга в `products` добавляется денормализованное поле:

```sql
ALTER TABLE products
    ADD COLUMN IF NOT EXISTS rating NUMERIC(3, 2) NOT NULL DEFAULT 0;
```

После добавления поля выполняется первичный расчёт по существующим отзывам:

```sql
UPDATE products AS p
SET rating = COALESCE(
    (
        SELECT ROUND(AVG(r.score)::numeric, 2)
        FROM reviews AS r
        WHERE r.product_id = p.id
    ),
    0
);
```

Если у товара нет отзывов, рейтинг равен `0.00`.

### 5.2. Функция атомарного оформления заказа `place_order`

Функция создаёт заказ, добавляет позицию и уменьшает остаток. Строка остатка
блокируется через `FOR UPDATE`, чтобы два параллельных заказа не смогли продать
один и тот же товар дважды.

```sql
CREATE OR REPLACE FUNCTION place_order(
    p_user_id   BIGINT,
    p_product_id BIGINT,
    p_qty       INT
)
RETURNS BIGINT
LANGUAGE plpgsql
AS $$
DECLARE
    v_order_id BIGINT;
    v_price    NUMERIC(12, 2);
    v_title    VARCHAR(255);
    v_stock    INT;
BEGIN
    IF p_qty IS NULL OR p_qty <= 0 THEN
        RAISE EXCEPTION 'Количество должно быть положительным: %', p_qty;
    END IF;

    SELECT p.price, p.title
    INTO v_price, v_title
    FROM products AS p
    WHERE p.id = p_product_id
      AND p.is_active = TRUE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Товар % не найден или неактивен', p_product_id;
    END IF;

    SELECT s.quantity
    INTO v_stock
    FROM stock AS s
    WHERE s.product_id = p_product_id
    FOR UPDATE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Для товара % нет записи об остатке', p_product_id;
    END IF;

    IF v_stock < p_qty THEN
        RAISE EXCEPTION
            'Недостаточно товара «%» на складе: запрошено %, доступно %',
            v_title, p_qty, v_stock;
    END IF;

    INSERT INTO orders (user_id, status, total_amount)
    VALUES (p_user_id, 'created', v_price * p_qty)
    RETURNING id INTO v_order_id;

    INSERT INTO order_items (order_id, product_id, quantity, unit_price)
    VALUES (v_order_id, p_product_id, p_qty, v_price);

    UPDATE stock
    SET quantity = quantity - p_qty,
        updated_at = now()
    WHERE product_id = p_product_id;

    RETURN v_order_id;
END;
$$;
```

Если товара не хватает, `RAISE EXCEPTION` прерывает функцию. Все изменения,
сделанные внутри функции, откатываются — «половинчатого» заказа не остаётся.

### 5.3. Функция расчёта выручки продавца `seller_revenue`

Функция использует локальную переменную и `SELECT ... INTO`. Отменённые заказы
не учитываются.

```sql
CREATE OR REPLACE FUNCTION seller_revenue(
    p_seller_id BIGINT,
    p_from      DATE,
    p_to        DATE
)
RETURNS NUMERIC(14, 2)
LANGUAGE plpgsql
AS $$
DECLARE
    v_revenue NUMERIC(14, 2);
BEGIN
    SELECT COALESCE(SUM(oi.quantity * oi.unit_price), 0)::numeric(14, 2)
    INTO v_revenue
    FROM products AS p
    JOIN order_items AS oi ON oi.product_id = p.id
    JOIN orders AS o ON o.id = oi.order_id
    WHERE p.seller_id = p_seller_id
      AND o.status <> 'cancelled'
      AND o.created_at::date BETWEEN p_from AND p_to;

    RETURN v_revenue;
END;
$$;
```

### 5.4. Триггер аудита изменения цены

Триггер срабатывает после `UPDATE` цены и записывает старое и новое значение
в `product_price_audit`:

```sql
CREATE OR REPLACE FUNCTION log_product_price_change()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    IF NEW.price IS DISTINCT FROM OLD.price THEN
        INSERT INTO product_price_audit (product_id, old_price, new_price)
        VALUES (OLD.id, OLD.price, NEW.price);
    END IF;

    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_product_price_audit
AFTER UPDATE OF price ON products
FOR EACH ROW
WHEN (OLD.price IS DISTINCT FROM NEW.price)
EXECUTE FUNCTION log_product_price_change();
```

Условие `WHEN` не даёт триггеру срабатывать, если цена фактически не изменилась.

### 5.5. Триггер поддержки среднего рейтинга

Триггер пересчитывает `products.rating` после добавления, изменения или удаления
отзыва. При изменении `product_id` пересчитываются оба товара — старый и новый.

```sql
CREATE OR REPLACE FUNCTION refresh_product_rating()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
DECLARE
    v_old_product_id BIGINT;
    v_new_product_id BIGINT;
BEGIN
    IF TG_OP = 'DELETE' THEN
        v_old_product_id := OLD.product_id;
    ELSIF TG_OP = 'UPDATE' THEN
        v_old_product_id := OLD.product_id;
        v_new_product_id := NEW.product_id;
    ELSE
        v_new_product_id := NEW.product_id;
    END IF;

    IF v_old_product_id IS NOT NULL THEN
        UPDATE products AS p
        SET rating = COALESCE(
            (
                SELECT ROUND(AVG(r.score)::numeric, 2)
                FROM reviews AS r
                WHERE r.product_id = v_old_product_id
            ),
            0
        )
        WHERE p.id = v_old_product_id;
    END IF;

    IF v_new_product_id IS NOT NULL
       AND v_new_product_id IS DISTINCT FROM v_old_product_id THEN
        UPDATE products AS p
        SET rating = COALESCE(
            (
                SELECT ROUND(AVG(r.score)::numeric, 2)
                FROM reviews AS r
                WHERE r.product_id = v_new_product_id
            ),
            0
        )
        WHERE p.id = v_new_product_id;
    END IF;

    IF TG_OP = 'DELETE' THEN
        RETURN OLD;
    END IF;

    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_refresh_product_rating
AFTER INSERT OR UPDATE OR DELETE ON reviews
FOR EACH ROW
EXECUTE FUNCTION refresh_product_rating();
```

## 6. Демонстрация транзакций

### 6.1. Успешная транзакция с `COMMIT`

Для демонстрации используется отдельный тестовый товар `id = 999001` с остатком
100 шт. и тестовый заказ `id = 999001`, чтобы не менять основные данные.

```sql
BEGIN;

INSERT INTO orders (id, user_id, status, total_amount, created_at)
OVERRIDING SYSTEM VALUE
VALUES (999001, 1, 'created', 2000.00, now());

INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES (999001, 999001, 2, 1000.00);

UPDATE stock
SET quantity = quantity - 2,
    updated_at = now()
WHERE product_id = 999001;

COMMIT;
```

Состояние до и после `COMMIT`:

```text
+---------------+--------------+
| orders_before | stock_before |
+---------------+--------------+
|          1500 |          100 |
+---------------+--------------+
```

```text
+----------+--------------+------------+----------+------------+
| order_id | total_amount | product_id | quantity | unit_price |
+----------+--------------+------------+----------+------------+
|   999001 |      2000.00 |     999001 |        2 |    1000.00 |
+----------+--------------+------------+----------+------------+
```

После `COMMIT` остаток тестового товара уменьшился с 100 до 98:

```text
+------------+--------------------+
| product_id | stock_after_commit |
+------------+--------------------+
|     999001 |                 98 |
+------------+--------------------+
```

Все три изменения — заказ, позиция и остаток — стали видимы и сохранены.

### 6.2. Транзакция с намеренной ошибкой и `ROLLBACK`

Повторяем сценарий, но после вставки заказа, позиции и уменьшения остатка
намеренно вызываем деление на ноль:

```sql
BEGIN;

INSERT INTO orders (id, user_id, status, total_amount, created_at)
OVERRIDING SYSTEM VALUE
VALUES (999002, 1, 'created', 1000.00, now());

INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES (999002, 999001, 1, 1000.00);

UPDATE stock
SET quantity = quantity - 1,
    updated_at = now()
WHERE product_id = 999001;

-- Намеренная ошибка.
SELECT 1 / 0;

ROLLBACK;
```

PostgreSQL сообщает:

```text
ОШИБКА: деление на ноль
```

После ошибки транзакция находится в состоянии aborted, а `ROLLBACK` отменяет все
её изменения. Проверка показывает, что второй заказ не появился, а остаток
остался на уровне 98:

```text
+----------------------------+----------------------+
| test_orders_after_rollback | stock_after_rollback |
+----------------------------+----------------------+
|                          1 |                   98 |
+----------------------------+----------------------+
```

Единственный тестовый заказ — это заказ `999001` из успешной транзакции. Заказа
`999002` нет, списание за него не сохранилось. Это и есть проявление атомарности:
либо все связанные изменения, либо ни одного.

### 6.3. Очистка демонстрационных данных

После демонстрации тестовый заказ и тестовый товар удаляются:

```sql
BEGIN;

DELETE FROM orders WHERE id IN (999001, 999002);
DELETE FROM products WHERE id = 999001;

COMMIT;
```

```text
+----------------------------+-------------------+
| total_orders_after_cleanup | test_product_rows |
+----------------------------+-------------------+
|                       1500 |                 0 |
+----------------------------+-------------------+
```

Количество заказов вернулось к исходным 1 500, тестового товара нет.

```sql
       oi.quantity,

FROM stock
WHERE product_id = 1;

```

```text
+--------------+
|           13 |
+--------------+

+--------------+

+--------------+

+--------------+

| order_id | user_id | status  | total_amount | product_id | quantity | unit_price |
+----------+---------+---------+--------------+------------+----------+------------+
|     1501 |       1 | created |      2166.00 |          1 |        2 |    1083.00 |
```

### 7.3. Нехватка товара: отсутствие частичных изменений

Вызываем функцию с количеством 1 000 000 при остатке 13. Исключение
перехватывается в `DO`-блоке, чтобы скрипт продолжил работу, и сравниваются
значения до и после:

```sql
DO $$
DECLARE
    v_orders_before BIGINT;
    v_stock_before  INT;
    v_orders_after  BIGINT;
    v_stock_after   INT;
BEGIN
    SELECT count(*) INTO v_orders_before FROM orders;
    SELECT quantity INTO v_stock_before FROM stock WHERE product_id = 1;

    BEGIN
        PERFORM place_order(1, 1, 1000000);
    EXCEPTION WHEN OTHERS THEN
        RAISE NOTICE 'Ожидаемая ошибка: %', SQLERRM;
    END;

    SELECT count(*) INTO v_orders_after FROM orders;
    SELECT quantity INTO v_stock_after FROM stock WHERE product_id = 1;

    RAISE NOTICE 'Заказы: % -> %, остаток товара 1: % -> %',
        v_orders_before, v_orders_after, v_stock_before, v_stock_after;
END;
$$;
```

Сообщения PostgreSQL:

```text
ЗАМЕЧАНИЕ: Ожидаемая ошибка: Недостаточно товара «Телефон Galaxy S №1»
на складе: запрошено 1000000, доступно 13
ЗАМЕЧАНИЕ: Заказы: 1500 -> 1500, остаток товара 1: 13 -> 13
```

Количество заказов и остаток не изменились. Функция не оставила ни заказа, ни
позиции заказа, ни списания остатка.

### 7.4. Триггер аудита изменения цены

Цена товара 1 увеличивается на 100 руб., затем возвращается обратно. В журнал
попадают две записи:

```sql
UPDATE products SET price = price + 100 WHERE id = 1;
-- ...
UPDATE products SET price = price - 100 WHERE id = 1;
```

```text
+----+------------+-----------+-----------+-------------------------------+------------+
```

```text

+---------------------+
```

Триггер автоматически сохранил старое и новое значение, время изменения и

### 7.5. Триггер пересчёта рейтинга

У товара 2 есть один отзыв с оценкой 1, поэтому его рейтинг равен `1.00`.
Добавляем второй отзыв с оценкой 5 — среднее должно стать `3.00`. После
`ROLLBACK` отзыв и изменение рейтинга отменяются.

```sql
BEGIN;

SELECT rating AS rating_before
FROM products
WHERE id = 2;

INSERT INTO reviews (user_id, product_id, score, comment, created_at)
VALUES (1, 2, 5, 'Тестовый отзыв для проверки триггера', now());

SELECT rating AS rating_after_insert
FROM products
WHERE id = 2;

ROLLBACK;
```

```text
+---------------+
| rating_before |
+---------------+
|          1.00 |
+---------------+

+---------------------+
| rating_after_insert |
+---------------------+
|                3.00 |
+---------------------+

+-----------------------+
| rating_after_rollback |
+-----------------------+
|                  1.00 |
+-----------------------+
```

Триггер пересчитал средний рейтинг сразу после вставки отзыва, а откат
транзакции вернул исходное значение.

## 8. Логика в базе данных и в приложении

### 8.1. Что уместно держать в базе данных

- **Транзакционное оформление заказа.** Создание заказа, позиций и списание
  остатка должны выполняться атомарно, иначе возможны «половинчатые» заказы или
  отрицательный остаток.
- **Ограничения целостности.** `NOT NULL`, `CHECK`, внешние ключи, уникальные
  индексы должны действовать независимо от того, какое приложение обращается к
  базе.
- **Блокировки и защита от гонок.** `SELECT ... FOR UPDATE` в `place_order`
  предотвращает одновременную продажу последней единицы товара двум покупателям.
- **Аудит критичных изменений.** Триггер цены фиксирует историю независимо от
  приложения.
- **Денормализованные вычисляемые поля.** Средний рейтинг товара удобно
  поддерживать триггером, чтобы все читатели видели одинаковое значение.
- **Единые сводные функции.** Например, `seller_revenue` гарантирует одинаковый
  расчёт выручки во всех отчётах.

### 8.2. Что лучше оставить в приложении

- пользовательские интерфейсы, корзину, оформление сценариев;
- уведомления, рекомендации, промоакции;
- интеграции с платёжными системами и службами доставки;
- оркестрацию нескольких операций и повторные попытки;
- часто меняющиеся бизнес-правила;
- сложную аналитику и отчётность, если она не требует единого серверного
  инварианта.

### 8.3. Вывод по размещению логики

В базе данных следует оставлять то, что связано с целостностью и одинаковым
поведением для всех клиентов: транзакции, ограничения, блокировки, аудит и
поддержание денормализованных полей. Прикладная логика, которая часто меняется
или зависит от внешних сервисов, должна оставаться в приложении. Такой гибридный
подход даёт надёжность хранения и гибкость разработки.

## 10. Контрольные вопросы

**1. Что такое транзакция и какими свойствами ACID она обладает?**
Транзакция — неделимая последовательность операций, которая применяется целиком
или не применяется вовсе. ACID: атомарность (всё или ничего), согласованность
(переход между корректными состояниями), изоляция (параллельные транзакции не
мешают друг другу) и долговечность (зафиксированные изменения сохраняются после
сбоя).

**2. Что делают команды `COMMIT` и `ROLLBACK`? Для чего нужен `SAVEPOINT`?**
`COMMIT` фиксирует изменения транзакции и делает их постоянными. `ROLLBACK`
отменяет все изменения незавершённой транзакции. `SAVEPOINT` создаёт внутри
транзакции точку, к которой можно откатиться частично командой
`ROLLBACK TO SAVEPOINT`, сохранив более ранние изменения.

**3. Приведите пример сценария в маркетплейсе, где необходима транзакция.**
Оформление заказа: нужно создать запись заказа, добавить позиции и уменьшить
остаток товара. Если на любом шаге произойдёт ошибка (например, товара не хватит),
все изменения должны откатиться, иначе останется заказ без позиций или остаток
уменьшится без заказа.

**4. Что обеспечивает атомарность и что — изоляция?**
Атомарность гарантирует, что все операции транзакции выполнятся как единое целое
или не выполнятся вовсе. Изоляция гарантирует, что параллельные транзакции не
видят незафиксированные изменения друг друга и их совместный результат
соответствует некоторому последовательному порядку.

**5. Что такое функция в PostgreSQL и какие конструкции предоставляет PL/pgSQL?**
Функция — серверный объект с именем, аргументами и возвращаемым значением.
PL/pgSQL предоставляет переменные (`DECLARE`), присваивание, `SELECT ... INTO`,
ветвления `IF`, циклы, `RETURN`, `RAISE EXCEPTION`, `RAISE NOTICE` и блоки
`EXCEPTION` для обработки ошибок.

**6. Как в функции PL/pgSQL обработать ошибку и прервать выполнение?**
Для прерывания используют `RAISE EXCEPTION`, который возбуждает исключение и
откатывает изменения текущей транзакции. Для перехвата применяют блок
`BEGIN ... EXCEPTION WHEN OTHERS THEN ... END;`. В обработчике можно записать
сообщение, выполнить компенсирующие действия или повторно возбудить исключение.

**7. Что такое триггер и в ответ на какие события он срабатывает?**
Триггер — серверный объект, автоматически вызывающий функцию при изменении данных.
События: `INSERT`, `UPDATE`, `DELETE`; для представлений — `INSTEAD OF`.
Триггер может срабатывать до (`BEFORE`) или после (`AFTER`) операции.

**8. Чем различаются триггеры `BEFORE` и `AFTER`, уровня строки и оператора? Что такое `NEW` и `OLD`?**
`BEFORE` выполняется до изменения и может проверить или скорректировать данные;
`AFTER` — после изменения, удобен для аудита и пересчёта связанных данных.
`FOR EACH ROW` вызывается для каждой строки, `FOR EACH STATEMENT` — один раз на
оператор. `NEW` содержит новую версию строки (для `INSERT` и `UPDATE`), `OLD` —
прежнюю (для `UPDATE` и `DELETE`).

**9. Для каких задач применяют триггеры? Приведите примеры из кейса маркетплейса.**
Триггеры применяют для аудита изменений, валидации, автоматического заполнения
полей и поддержания денормализованных значений. В маркетплейсе это журнал
изменения цен, пересчёт среднего рейтинга товара, обновление `updated_at`,
проверка допустимости остатка или статуса.

**10. Каковы достоинства и недостатки размещения бизнес-логики на стороне СУБД?**
Достоинства: единые правила для всех приложений, близость вычислений к данным,
гарантия целостности на уровне хранилища, меньше передачи данных по сети.
Недостатки: сложнее тестировать и отлаживать, привязка к конкретной СУБД, нагрузка
на сервер, необходимость версионирования серверного кода. Поэтому в БД оставляют
критичную целостность, а прикладную логику чаще держат в приложении.
