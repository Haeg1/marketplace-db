## 3. Теоретическая часть

### 3.1. Оконная функция и конструкция `OVER`

Оконная функция вычисляет значение над набором строк, связанных с текущей строкой.
В отличие от агрегатной функции с `GROUP BY`, она **не схлопывает** строки: каждая
исходная строка остаётся в результате, а рядом появляется вычисленное значение.
Синтаксис обязательной конструкции:

```sql
функция(...) OVER (
    PARTITION BY ...
    ORDER BY ...
    ROWS BETWEEN ... AND ...
)
```

Оконные функции вычисляются после `WHERE`, `GROUP BY` и `HAVING`, но до `ORDER BY`
и `LIMIT`. Поэтому в них уже доступны результаты группировки, но отфильтровать
оконную функцию напрямую в `WHERE` нельзя — нужен внешний запрос или CTE.

### 3.2. `PARTITION BY`, `ORDER BY` и рамка окна

- `PARTITION BY` делит строки на независимые разделы. Нумерация и суммы начинаются
  заново в каждом разделе. В отличие от `GROUP BY`, строки не объединяются.
- `ORDER BY` внутри `OVER` задаёт порядок строк в окне. Он критичен для ранжирующих
  функций, нарастающих итогов и `LAG`/`LEAD`.
- Рамка (`frame`) ограничивает строки окна относительно текущей: `ROWS` считает
  физические строки, `RANGE` — диапазон значений по `ORDER BY`. Для нарастающего
  итога используют `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`.

Если `PARTITION BY` не указана, окном считаются все строки результата. Если не указана
рамка, действует значение по умолчанию; при наличии `ORDER BY` это
`RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, то есть в накопление включаются
текущая строка и все её «ровесники» по ключу сортировки.

### 3.3. Ранжирующие функции

| Функция | Поведение при равных значениях | Пример |
|---|---|---|
| `ROW_NUMBER()` | номера всегда уникальны | 1, 2, 3, 4 |
| `RANK()` | равные значения получают одинаковый ранг, затем идёт пропуск | 1, 1, 3, 4 |
| `DENSE_RANK()` | равные значения получают одинаковый ранг без пропусков | 1, 1, 2, 3 |
| `NTILE(n)` | делит строки на `n` примерно равных групп | 1, 1, 2, 2, 3 |

`ROW_NUMBER()` часто используют для топ-N: нумеруют строки внутри группы, а затем
во внешнем запросе оставляют номера не больше N.

### 3.4. Агрегатные функции как оконные, `LAG` и `LEAD`

Любую агрегатную функцию можно использовать как оконную, добавив `OVER`:

- `SUM(x) OVER (ORDER BY day)` — нарастающий итог;
- `SUM(x) OVER (PARTITION BY category_id)` — итог по разделу без потери строк;
- `x / SUM(x) OVER (PARTITION BY category_id)` — доля строки в сумме раздела.

Функции смещения `LAG(column)` и `LEAD(column)` возвращают значение из предыдущей
или следующей строки окна. Они применяются для сравнения с предыдущим периодом,
расчёта прироста и проверки тренда. `FIRST_VALUE` и `LAST_VALUE` возвращают первое
и последнее значение в рамке; для `LAST_VALUE` часто требуется явно расширить рамку
до `UNBOUNDED FOLLOWING`, иначе по умолчанию она заканчивается на текущей строке.

### 3.5. Топ-N в группе и сравнение с `GROUP BY`

Задача «три самых дорогих товара в каждой категории» решается в два шага:

1. оконная функция `ROW_NUMBER()` нумерует товары внутри категории;
2. внешний запрос или CTE оставляет строки с `rn <= 3`.

Оконная функция удобнее обычной группировки, когда нужно сохранить детальные строки
рядом со сводным показателем. `GROUP BY` вернул бы только агрегаты и потерял бы
названия товаров, цены и другие исходные атрибуты. Если же нужно одновременно
показать продавца, его выручку и общую выручку категории, оконная сумма
`SUM(...) OVER (PARTITION BY category_id)` добавляет итог к каждой строке без
дополнительного соединения.

```sql
SELECT c.name AS category,
       p.title AS product_name,
       p.price AS price_rub,
       ROW_NUMBER() OVER (
           PARTITION BY p.category_id
           ORDER BY p.price DESC, p.id

       RANK() OVER w AS rank,
       DENSE_RANK() OVER w AS dense_rank
FROM products AS p
JOIN categories AS c ON c.id = p.category_id
WINDOW w AS (

)
ORDER BY p.category_id, p.price DESC, p.id;
```

#### Запрос 1a. Разница между ROW_NUMBER, RANK и DENSE_RANK на равных ценах

**Пояснение.** В текущем наборе точные цены внутри одной категории не повторяются,
поэтому для этих строк все три функции дали одинаковые значения. Разница проявляется
на равных ценах. Ниже — учебный пример с повторяющимися ценами:

```sql
WITH demo(category, product_name, price) AS (
    VALUES
        ('Смартфоны', 'Товар A', 50000),
        ('Смартфоны', 'Товар B', 50000),
        ('Смартфоны', 'Товар C', 40000),
        ('Смартфоны', 'Товар D', 40000),
        ('Смартфоны', 'Товар E', 30000)
)
SELECT category,
       product_name,
       price,
       ROW_NUMBER() OVER (
           PARTITION BY category
           ORDER BY price DESC, product_name
       ) AS row_number,
       RANK() OVER (
           PARTITION BY category
           ORDER BY price DESC
       ) AS rank,
       DENSE_RANK() OVER (
           PARTITION BY category
           ORDER BY price DESC
       ) AS dense_rank
FROM demo
ORDER BY category, price DESC, product_name;
```

```text
+-----------+--------------+-------+------------+------+------------+
| category  | product_name | price | row_number | rank | dense_rank |

| Смартфоны | Товар A      | 50000 |          1 |    1 |          1 |
| Смартфоны | Товар B      | 50000 |          2 |    1 |          1 |
| Смартфоны | Товар C      | 40000 |          3 |    3 |          2 |
| Смартфоны | Товар D      | 40000 |          4 |    3 |          2 |
| Смартфоны | Товар E      | 30000 |          5 |    5 |          3 |
+-----------+--------------+-------+------------+------+------------+
```

Видно, что `ROW_NUMBER` всегда даёт уникальные номера `1, 2, 3, 4, 5`;
`RANK` после двух первых мест переходит к `3` и затем к `5`, пропуская `2` и `4`;
`DENSE_RANK` не пропускает номера и даёт `1, 1, 2, 2, 3`.

### Запрос 2. Три самых дорогих товара в каждой категории

**Назначение:** пронумеровать товары внутри категории по убыванию цены в CTE,
а затем оставить только строки с номером `rn <= 3`. Это классический топ-N
в группе: оконная функция считает номер, внешний запрос фильтрует результат.

```sql
WITH ranked AS (
    SELECT c.name AS category,
           p.title AS product_name,
           p.price AS price_rub,
           ROW_NUMBER() OVER (
               PARTITION BY p.category_id
               ORDER BY p.price DESC, p.id
           ) AS rn
    FROM products AS p
    JOIN categories AS c ON c.id = p.category_id
)
SELECT category,
       rn,
       product_name,
       price_rub
FROM ranked
WHERE rn <= 3
ORDER BY category, rn;
```

### Запрос 3. Нарастающий итог выручки по дням

**Назначение:** посчитать выручку каждого дня, а затем оконной агрегатной функцией
`SUM(...) OVER (ORDER BY day)` получить накопительную сумму от первого дня до
текущего.

```sql
WITH daily AS (
    SELECT o.created_at::date AS day,
           SUM(oi.quantity * oi.unit_price) AS day_revenue
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.id
    GROUP BY o.created_at::date
)
SELECT day,
       ROUND(day_revenue, 2) AS day_revenue,
       ROUND(
           SUM(day_revenue) OVER (
               ORDER BY day
               ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
           ),
           2
       ) AS running_total
FROM daily
ORDER BY day;
```

### Запрос 4. Доля выручки продавца в выручке его категории

**Назначение:** для каждой пары «категория + продавец» показать выручку, общую
выручку категории и процент продавца. Общая выручка добавляется оконной суммой
`SUM(...) OVER (PARTITION BY category_id)`, поэтому детальные строки продавцов
не сворачиваются.

```sql
WITH seller_category_revenue AS (
    SELECT p.category_id,
           p.seller_id,
           SUM(oi.quantity * oi.unit_price) AS revenue
    FROM products AS p
    JOIN order_items AS oi ON oi.product_id = p.id
    GROUP BY p.category_id, p.seller_id
)
SELECT c.name AS category,
       s.store_name AS seller,
       ROUND(scr.revenue, 2) AS revenue,
       ROUND(
           SUM(scr.revenue) OVER (PARTITION BY scr.category_id),
           2
       ) AS category_revenue,
       ROUND(
           100 * scr.revenue
           / SUM(scr.revenue) OVER (PARTITION BY scr.category_id),
           2
       ) AS share_percent
FROM seller_category_revenue AS scr
JOIN categories AS c ON c.id = scr.category_id
JOIN sellers AS s ON s.id = scr.seller_id
ORDER BY scr.category_id, revenue DESC, s.store_name;
```

**Фрагмент результата** (категория «Смартфоны», все 7 продавцов):

### Запрос 5. Сравнение выручки с предыдущим и следующим днём через `LAG` и `LEAD`

**Назначение:** для каждого дня показать выручку, выручку предыдущего дня,
абсолютный прирост, процент прироста и выручку следующего дня. `LAG` даёт предыдущую
строку окна, `LEAD` — следующую.

```sql
WITH daily AS (
    SELECT o.created_at::date AS day,
           SUM(oi.quantity * oi.unit_price) AS day_revenue
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.id
    GROUP BY o.created_at::date
)
SELECT day,
       ROUND(day_revenue, 2) AS day_revenue,
       ROUND(
           LAG(day_revenue) OVER (ORDER BY day),
           2
       ) AS prev_day_revenue,
       ROUND(
           day_revenue - LAG(day_revenue) OVER (ORDER BY day),
           2
       ) AS day_over_day_change,
       ROUND(
           100 * (
               day_revenue - LAG(day_revenue) OVER (ORDER BY day)
           ) / NULLIF(LAG(day_revenue) OVER (ORDER BY day), 0),
           2
       ) AS growth_percent,
       ROUND(
           LEAD(day_revenue) OVER (ORDER BY day),
           2
       ) AS next_day_revenue
FROM daily
ORDER BY day;
```

### Запрос 6. Та же задача, что и в запросе 4, но через `GROUP BY`

**Назначение:** показать альтернативное решение без оконной функции. Сначала
считается выручка по парам «категория + продавец», затем отдельным агрегатом —
выручка категории, после чего два результата соединяются по `category_id`.

```sql
WITH seller_category_revenue AS (
    SELECT p.category_id,
           p.seller_id,
           SUM(oi.quantity * oi.unit_price) AS revenue
    FROM products AS p
    JOIN order_items AS oi ON oi.product_id = p.id
    GROUP BY p.category_id, p.seller_id
),
category_revenue AS (
    SELECT category_id,
           SUM(revenue) AS category_revenue
    FROM seller_category_revenue
    GROUP BY category_id
)
SELECT c.name AS category,
       s.store_name AS seller,
       ROUND(scr.revenue, 2) AS revenue,
       ROUND(cr.category_revenue, 2) AS category_revenue,
       ROUND(
           100 * scr.revenue / cr.category_revenue,
           2
       ) AS share_percent
FROM seller_category_revenue AS scr
JOIN category_revenue AS cr ON cr.category_id = scr.category_id
JOIN categories AS c ON c.id = scr.category_id
JOIN sellers AS s ON s.id = scr.seller_id
ORDER BY scr.category_id, revenue DESC, s.store_name;
```

**Фрагмент результата** (категория «Смартфоны»):

```text

| Смартфоны | ТехноМир №1         | 3221984.90 |      21032220.00 |         15.32 |
| Смартфоны | ТехноМир №121       | 3021893.60 |      21032220.00 |         14.37 |

| Смартфоны | МегаМаркет №101     | 2927382.80 |      21032220.00 |         13.92 |

| Смартфоны | Одежда Plus №21     | 2596566.10 |      21032220.00 |         12.35 |

```

**Пояснение.** Результат полностью совпадает с запросом 4, но получен иначе:
`GROUP BY` сворачивает строки до уровня «категория + продавец», затем отдельный
`GROUP BY` считает итог категории, а `JOIN` добавляет его к каждой строке. Оконная
функция в запросе 4 делает то же самое в одном проходе по агрегированному набору:
`SUM(...) OVER (PARTITION BY category_id)` не требует второго агрегата и соединения
и сохраняет все строки продавцов. Поэтому для доли в группе оконный вариант короче,
читабельнее и обычно эффективнее; `GROUP BY` уместен, когда нужны только сводные
строки без детализации.

## 6. Контрольные вопросы

**1. Чем оконная функция отличается от агрегатной с `GROUP BY`?**
Агрегатная функция с `GROUP BY` сворачивает группу строк в одну строку результата.
Оконная функция вычисляет значение по окну, но сохраняет каждую исходную строку,
поэтому рядом с детальными данными можно показать ранг, сумму по группе или
нарастающий итог.

**2. Что задаёт `PARTITION BY`?**
Делит результат на независимые разделы. Оконная функция вычисляется отдельно в
каждом разделе: нумерация, суммы и `LAG`/`LEAD` начинаются заново. В отличие от
`GROUP BY`, строки не объединяются.

**3. Зачем нужен `ORDER BY` внутри `OVER`?**
Он задаёт порядок строк в окне. Без него нельзя осмысленно использовать
`ROW_NUMBER`, `RANK`, `LAG`, `LEAD` и нарастающий итог. Для агрегатных функций без
`ORDER BY` окном обычно является весь раздел.

**4. Чем `ROW_NUMBER` отличается от `RANK` и `DENSE_RANK`?**
`ROW_NUMBER` всегда выдаёт уникальные последовательные номера. `RANK` даёт одинаковый
ранг равным строкам, но затем пропускает номера (`1, 1, 3`). `DENSE_RANK` тоже даёт
одинаковый ранг равным строкам, но без пропусков (`1, 1, 2`).

**5. Что такое рамка окна и чем `ROWS` отличается от `RANGE`?**
Рамка ограничивает набор строк, участвующих в вычислении, относительно текущей
строки. `ROWS` считает физические строки, `RANGE` — диапазон значений по `ORDER BY`.
Для нарастающего итога обычно используют
`ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`.

**6. Чем `LAG` отличается от `LEAD`?**
`LAG` возвращает значение из предыдущей строки окна, `LEAD` — из следующей. Обе
функции принимают необязательный размер смещения и значение по умолчанию; у первой
и последней строки соответствующее значение может быть `NULL`.

**7. Почему оконную функцию нельзя использовать в `WHERE`?**
Потому что `WHERE` выполняется раньше оконных функций. Сначала фильтруются строки,
затем при необходимости выполняется группировка, и только после этого вычисляются
окна. Чтобы отфильтровать результат окна, нужен внешний запрос или CTE, как в
запросе 2.

**8. Когда оконная функция удобнее `GROUP BY`?**
Когда нужны и детальные строки, и сводный показатель: рейтинг товаров, доля продавца
в категории, нарастающий итог, сравнение с предыдущим днём. `GROUP BY` возвращает
только агрегаты; чтобы добавить их к детальным строкам, приходится делать
дополнительный `JOIN` или подзапрос.

**9. Что произойдёт, если в запросе 4 убрать `PARTITION BY`?**
`SUM(scr.revenue) OVER ()` посчитает общую выручку по всем категориям, и доля будет
считаться от общего оборота, а не от оборота категории. Это изменит смысл показателя.

**10. Влияет ли порядок строк в `OVER` на результат агрегатной функции?**
Для суммы по всему разделу без `ORDER BY` — нет. Для нарастающего итога — да:
именно `ORDER BY` определяет, какие строки считаются предыдущими. Для `RANK` и
`ROW_NUMBER` порядок также полностью определяет номера.
